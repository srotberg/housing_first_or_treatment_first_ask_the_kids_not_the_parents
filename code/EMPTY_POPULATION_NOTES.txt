THREE THINGS THIS RUN TURNED UP THAT ARE NOT YET WRITTEN DOWN ANYWHERE
----------------------------------------------------------------------

(1) THE BUDGET CHECKER DOES NOT KNOW ABOUT THE PRICE OF TREATMENT.

397,788 lines of this log -- of 3,581,728, and the reason the file is 174 MB
rather than about 15 MB -- are

    budget does not clear by   2.0000000000000018E-002

and every distinct residual in the file rounds to 0.02, which is exactly
money_cost_of_treatment for this vector. It is not a coincidence and it is not
noise:

  - the charge is applied at :20259, inside the addiction branch, and it
    reduces total_consumption_choice_1 only;
  - check_budget_constraint_clears (:21557) rebuilds the residual at :21651 as
    after_tax_wealth_net_of_expenses_1 minus (savings + (1+tau_c)*consumption),
    with no treatment term anywhere in it.

So the household pays for treatment out of consumption, the checker never
subtracts the payment, and it reports the full price as a violation for every
state in which someone is in treatment. tau_u is 0.579 at this point, so that
is a lot of states.

This is a WRITE-ONLY diagnostic -- the whole thing sits inside a write block
and changes no policy, no value function and no distribution -- so it did NOT
cause the empty population, and the moments above are unaffected. But
money_cost_of_treatment landed on 31 August, the same window as the breakage,
so it is worth being explicit that it was looked at and cleared. What it does
cost is an order of magnitude of log size and the ability to see anything else
in the file. Worth deciding whether the fix is to add the treatment term to the
checker or to note the payment as a genuine leak out of the household budget
identity -- it leaves the household and goes to a provider that is not in the
accounting. I have NOT touched the source.

(2) code/newborn_parent_share.dat IS TRACKED, IS STALE, AND SURVIVES A COLD
    START.

The committed copy is FOUR lines:

    1.000000000000000
    0.000000000000000
    0.000000000000000
    0.000000000000000

which is the OLD reshape((/1,0,0,0/)) shape. The array is now
(employment_grid_size, 0:1, 1:2) = (17,0:1,1:2) = 68 elements. run_one_point.sh
:214 removes calibration_state.dat and calibration_distribution*.dat but NOT
this file, so it is the one piece of previous state that a "cold" start keeps.

Reading 4 values into a 68-element array hits end of file, sets iostat, and the
fallback at :32249 rebuilds the shares from the unconditional distribution --
so today it degrades safely. It is worth knowing that the only thing standing
between a stale banked file and a silently wrong newborn draw is that fallback
plus the sum(...)<=1e-12 seed, and that the file in git no longer has the shape
the code expects.

(3) THE BANKED SHARES ARE ZEROED AT STARTUP, BEFORE THE SEED RUNS.

Call order on a cold start is:

    apply_param_handover (:32482) -> write_calibration_state (:32719)
    calibrating_model (:32869)    -> read_calibration_state (:32887)
                                  -> GKKOC_...employment_process (:32935)

The handover banks the state FIRST, and at that moment newborn_parent_share is
still at its declaration value of 0, so :32023 writes 68 zeros over
newborn_parent_share.dat before the seed at :25205 has ever executed. That is
why the working copy of that file is 68 zero lines after this run even though
the run itself was healthy -- it is a pre-seed snapshot, not a measurement.

The consequence to watch: a resumed run reads those 68 zeros with iostat==0, so
the "no banked newborn parent shares" fallback does NOT fire; it is rescued
only because the seed's sum(...)<=1e-12 test then catches it. Two independent
safety nets currently overlap on this. If either moves, the population dies
again and, on the evidence of the dead points, it dies silently except for
theta = -1.0.


A CAVEAT ON THIS MEASUREMENT
----------------------------

newborn_parent_share reads (1, 0, 0, 0) at all 61 sweeps, because the shares
are rebuilt by the aggregation (:8844) which runs AFTER the distribution, and
this is a single-loop measurement run. So this point is measured with NO
intergenerational transmission: every newborn is drawn from a clean, housed,
unpenalised parent mixture. That is the documented cold-start behaviour -- the
comment at :32005 says so directly -- and not a bug, but it means the child
penalty channel contributes nothing to the numbers in the table above. The
0.880/0.119 split found by the aggregation is banked for a second loop that
this run never takes.
