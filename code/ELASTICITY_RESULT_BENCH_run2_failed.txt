LIKELY CAUSE (read from the log and the source; NOT tested by a run)
-----------------------------------------------------------------
The elasticity block sits inside print_all_moments, which calibrating_model calls at line 52248
of 77803322 -- AFTER that loop pass's parameter update block (e.g. addiction_onset_base at
49058, kappa_phi_d_level at 49314). So:
  - the base moments printed (MOMENT b, ELASTICITY_DIAG base) are statistics of the distribution
    and policies solved under the PRE-update parameters;
  - both solves inside the elasticity block -- at the raised price and, now, at the base price --
    use the POST-update parameters on the held distribution.
Evidence: in block 1 the base-price re-solve gives b = 0.0824349 (BLOCK MOVE), against MOMENT b
0.0718856 at the same price and distribution; the gap is the parameter update, not the price.
Once the parameters stop moving (blocks 4-5) the two agree to ~1e-9 relative. Consequences:
  (1) each block's elasticity mixes the +10% price step with that pass's parameter update (small
      at the last block, where the update is small, but not zero by construction);
  (2) the state left behind (policies, value functions, statistics from the re-solve) is not the
      one the next pass would otherwise start from, so the trajectory diverges from the paper's
      from block 2 on whether or not the base price is re-solved -- run 1 and this run follow
      nearly the same path (block-2 h_1 6.0935e-3 in run 1, 6.0932e-3 here; paper 6.4900e-3).
      Restoring the benchmark path would need the pre-measurement state SAVED and RESTORED (policies,
      value functions, statistics), or the measurement moved to a point where parameters and
      policies are consistent (e.g. once, after the loop exits, before the save). Not done here.
Note also that block 1, printed before any elasticity measurement has fed back (ELASTICITY_DIAG
base appears 5 times, once per block), is already off the paper by ~4e-5 (MOMENT b 0.07188565 vs
0.07188836; h_1 7.07797e-3 vs 7.07799e-3), and run 1's block 1 differed again (h_1 7.07808e-3).
Unexplained here; run-to-run floating-point order under OpenMP is one candidate, not tested. It is
two orders smaller than the block-2 divergence.
